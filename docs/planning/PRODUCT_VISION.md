# Kladje product vision

**Proposed direction for v1.0 · 23 November 2026.** Kladje should be the editor a writer can open from the file manager, use offline for five minutes or an afternoon, and close with confidence about where every edit went. Its unit of work is an ordinary Markdown file. The audience includes people editing a README, meeting notes, instructions or an article with local images. Each should be able to hand their file to someone using a different editor.

## What the reference editors teach us

| Reference | Workflow worth learning from | Decision for Kladje |
| --- | --- | --- |
| Typora lets writers select, drop or paste images and choose where referenced files live. [Image handling](https://support.typora.io/Images/) | The hard part of inserting a screenshot is knowing where the bytes went and whether the link travels. | Start with Insert Local Image and an ordinary relative path. For a pasted bitmap, choose an explicit local destination once the document has a home. |
| MarkText offers live formatted editing, source, focus and typewriter modes. [Project feature list](https://github.com/marktext/marktext#features) | Different tasks benefit from different levels of visual distraction. | Keep Kladje’s source and preview layouts. Source-only plus a comfortable line length already addresses much of the writing use case. Defer a second editing model. |
| Obsidian keeps local recovery snapshots and lets users inspect and recover earlier text. [File recovery](https://obsidian.md/help/plugins/file-recovery) | A draft and the current file on disk can both be worth keeping. | Offer time-stamped local recovery and a Save Copy path at conflicts. Recovery should also work for a never-named draft. |
| Zettlr offers single-file export, profiles and project-wide publishing. [Export documentation](https://docs.zettlr.com/en/export/) | Export complexity pays off when writers repeatedly need specific publishing formats. | Deliver two predictable outputs first. A shared HTML file should explain or carry its image dependencies, and the PDF should match the preview. |
| VS Code can jump to Markdown headings, follow links and navigate between source and preview. [Markdown editing](https://code.visualstudio.com/docs/languages/markdown) | Heading navigation saves time even inside one file. | Add a keyboard heading picker backed by the renderer’s positions. A persistent project tree would consume width in every writing session. |

Use CommonMark as the baseline, list the supported GFM extensions, and separately document Kladje extras such as math, footnotes and callouts. Sanitized HTML, generated heading IDs and hidden frontmatter affect visible output. Maintain a small, named compatibility corpus with those deliberate differences. [CommonMark specification](https://spec.commonmark.org/current/) · [GFM specification](https://github.github.com/gfm/)

## Product decisions

1. **What already works well?** A new user can experiment in the bundled guide, see both the source and output, continue a list, search and undo. The same Rust renderer powers preview and HTML. Math, code and an accessible document structure already work on the tested Mac. The small window chrome gives the document most of the space. Evidence is in the [native checks](UX_REVIEW.md) and [core test results](PROJECT_AUDIT.md).
2. **What is missing?** Trustworthy save and recovery under interruption, externally edited files, functioning external links, a recent-files list and a straightforward path from a local image to a portable document. There is also too little evidence to make three-platform reliability or large-document speed promises.
3. **What comes before new features?** Give every buffer and disk version an identity, protect the last good file and recovery snapshot, and make conflicts visible. Capture those guarantees in tests before changing menu structure or adding modes. A wrong “saved” indicator is more consequential than a missing command.
4. **What has the most everyday value?** Open Recent, jump to a heading, insert a local image, readable search and keyboard navigation, and knowing whether a file is saved, externally changed or recovered. A visible way to save a copy is valuable even to someone who never learns another shortcut.
5. **What should we deliberately avoid?** A plugin runtime, vault or graph index, collaboration accounts, automatic image upload, a general-purpose publishing engine and an independently editable rich-text view. Each brings a second storage, security or document model to maintain. Existing format shortcuts and a single source of truth cover the target tasks. Defer tabs until observed switching friction exceeds what Recent and separate documents can address.
6. **What differentiates Kladje?** Someone should be able to inspect the Markdown, change it with another program, return to the same passage and understand what changed. Keep local resources explicit, preserve unfamiliar content, and make HTML/PDF output predictable. That promise is testable with two editors, two folders and a network connection switched off.
7. **What counts as a complete v1.0?** All P0 and P1 release gates, plus the small P2 subset of Open Recent and jump-to-heading. One document per window, source/split/preview, keyboard formatting, find/replace, list continuation, validated file types, normal and conflict saves, local recovery, accessible navigation, local image insertion, portable HTML and tested print-to-PDF. Document the supported subset of import and the tested performance envelope. Label a platform stable only after its native gates pass.
8. **What is the best order?** Establish a failing save regression → fix replacement and revision handling → protect external versions and drafts → close input/preview trust gaps → verify everyday editing and output on each OS → add Recent and outline → evaluate optional conveniences. Each step has an independent exit test in the [roadmap](DEVELOPMENT_ROADMAP.md).
9. **Which decisions need the owner?** The following defaults are proposals. They affect observable behavior or ongoing release obligations.

| Decision | Proposed default | Consequence of accepting it |
| --- | --- | --- |
| Save and recovery contract | Explicit Save for the original. Periodic private crash drafts, including untitled documents. Keep a prior good snapshot until a new one is durable. Establish retention and a clear-history control. | The app must explain private on-disk drafts on shared machines. A failed replacement offers Retry and Save Copy. |
| Format fidelity | Preserve an existing UTF-8 BOM and uniform LF/CRLF. Disclose mixed endings or unsupported encodings before an in-place conversion. Offer UTF-8 Save Copy. For symlinks, preserve the link and edit its intended target after validation, or require Save Copy if ambiguous. | Some unusual files take an extra step. A normal save no longer silently changes file identity or representation. |
| Images, remote content and HTML | Local images relative to a saved document, explicit approval for other directories, remote images off until enabled for the document. For HTML exported elsewhere, default to portable local assets with a documented size limit and missing-asset warning. | Offline opens are predictable. Export may be larger or require choosing an asset folder. |
| Document and window model | Keep one active document in the v1 window. Support rapid switching through Recent and an outline. Give recoveries per-document/per-instance identities even in this model. | Avoids introducing tab-specific history and close semantics while leaving room for future independent windows. |
| Platforms and release bar | Aim for macOS, Windows and Linux. Name a maintained baseline for each, designate native testers, and allow a staged release where evidence arrives at different times. | The README can name precisely which builds, file operations and print paths have been qualified. |

The [feature matrix](FEATURE_MATRIX.md) gives each candidate a price in implementation and maintenance. A new feature earns its place when it removes a recurring step from writing, saving, navigating or sharing one document.
